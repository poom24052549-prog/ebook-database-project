# คำอธิบายการปรับแบบข้อมูลให้อยู่ในรูปแบบบรรทัดฐานขั้นที่ 3 (3NF)
**โครงงาน:** Mini Project Database ร้านขาย E-Book  
**รายวิชา:** Database Mini Project  

---

## 1. การวิเคราะห์ตามหลักการนอร์มัลไลเซชัน (Normalization Steps)

### รูปแบบบรรทัดฐานขั้นที่ 1 (First Normal Form - 1NF)
* **เกณฑ์:** ทุกคอลัมน์ต้องเก็บค่าที่เป็นอะตอมมิก (Atomic Value) ไม่มีกลุ่มข้อมูลซ้ำ (Repeating Groups) และแต่ละตารางต้องมี Primary Key
* **การดำเนินการในระบบ:**
  * แยกรายการสั่งซื้อออกจากตารางคำสั่งซื้อหลัก โดยไม่เก็บรหัสหนังสือเป็นลิสต์คั่นด้วยจุลภาคในแถวเดียว แต่สร้างเป็นตารางลูก `order_items`
  * แยกผู้แต่งและหมวดหมู่ออกเป็นตารางเฉพาะ (`authors`, `categories`) โดยไม่นำประวัติหรือรายละเอียดของผู้แต่งมาอัดรวมในตาราง `ebooks`
  * กำหนด Primary Key ที่ชัดเจนในทุกตาราง (เช่น `order_id`, `ebook_id`, `user_id`)

### รูปแบบบรรทัดฐานขั้นที่ 2 (Second Normal Form - 2NF)
* **เกณฑ์:** ต้องผ่าน 1NF แล้ว และทุก Attribute ที่ไม่ใช่คีย์หลักต้องขึ้นตรงกับคีย์หลักทั้งตัว (No Partial Functional Dependency)
* **การดำเนินการในระบบ:**
  * ในตารางที่มีความสัมพันธ์กลุ่ม เช่น `cart_items` หรือ `order_items` คีย์หลักถูกออกแบบเป็น surrogate key (`order_item_id`) และคุณลักษณะทั้งหมด เช่น `unit_price`, `quantity`, `subtotal` มีความสัมพันธ์ตรงกับรายการย่อยนั้นๆ ไม่ขึ้นอยู่กับส่วนใดส่วนหนึ่งของ Composite Key

### รูปแบบบรรทัดฐานขั้นที่ 3 (Third Normal Form - 3NF)
* **เกณฑ์:** ต้องผ่าน 2NF แล้ว และไม่มีการพึ่งพาแบบถ่ายทอดระหว่าง Attribute ที่ไม่ใช่คีย์หลัก (No Transitive Functional Dependency: $X \rightarrow Y$ และ $Y \rightarrow Z$)
* **การดำเนินการในระบบ:**
  * **บทบาทผู้ใช้:** แยกข้อมูลบทบาท (`roles`) ออกจาก `users` โดย `users` เก็บเฉพาะ `role_id` เท่านั้น เพื่อไม่ให้รายละเอียดบทบาทขึ้นกับชื่อบทบาทที่ขึ้นกับ `user_id` อีกทอดหนึ่ง
  * **หมวดหมู่หนังสือ:** แยก `categories` ออกจาก `ebooks` โดยเก็บเพียง `category_id` ป้องกันความซ้ำซ้อนของชื่อหมวดและคำอธิบายหมวด
  * **ผู้แต่งหนังสือ:** แยก `authors` ออกจาก `ebooks` โดยเก็บเพียง `author_id`
  * **การชำระเงิน:** แยก `payments` ออกจาก `orders` เพื่อให้ข้อมูลช่องทางชำระเงิน หลักฐานสลิป และสถานะการตรวจสอบการโอนขึ้นตรงกับ `payment_id`

## 2. การเก็บข้อมูลซ้ำเพื่อความถูกต้องทางธุรกิจและประสิทธิภาพการรายงาน (Controlled Redundancy & Historical Preservation)

ใบงานข้อ 4 ระบุว่า: *"ออกแบบให้อยู่ใน 3NF ในขอบเขตที่เหมาะสม หรืออธิบายเหตุผลหากเก็บข้อมูลซ้ำเพื่อรายงาน"*  
ในระบบนี้มี 2 จุดสำคัญที่มีการเก็บข้อมูลเพื่อวัตถุประสงค์เฉพาะ ดังนี้:

### จุดที่ 1: การเก็บ `unit_price` ในตาราง `order_items`
* **เหตุผลทางธุรกิจ (Price Immutability):** ราคาหนังสือในตาราง `ebooks` อาจมีการเปลี่ยนแปลงหรือจัดโปรโมชั่นในอนาคต หากเราดึงราคาจาก `ebooks.price` โดยตรงในการคำนวณย้อนหลัง ยอดขายในอดีตจะผิดเพี้ยนไป ดังนั้นการ snapshot ราคา ณ วันที่เกิดคำสั่งซื้อเก็บไว้ใน `order_items.unit_price` จึงเป็นมาตรฐานสากลของระบบ E-Commerce เพื่อความถูกต้องของการทำบัญชีและประวัติคำสั่งซื้อ

### จุดที่ 2: การเก็บ `total_amount` ในตาราง `orders`
* **เหตุผลด้านประสิทธิภาพ (Query Optimization for Dashboards & Reporting):** ในการทำรายงานวิเคราะห์ยอดขายตามช่วงเวลา หรือแดชบอร์ดสรุปยอดขายของร้านค้า การเก็บ `total_amount` สรุปไว้ที่ระดับหัวตาราง `orders` ช่วยลด Overhead จากการต้องทำ `SUM(subtotal)` ผ่านตาราง `order_items` หลายหมื่นเรคอร์ดในทุกครั้งที่มีการเปิดดูหน้าแรกหรือสรุปยอดขาย โดยระบบควบคุมความสอดคล้อง (Data Consistency) ด้วย Logic ในระดับแอปพลิเคชันและการคำนวณที่สอดคล้องกันอย่างสมบูรณ์
